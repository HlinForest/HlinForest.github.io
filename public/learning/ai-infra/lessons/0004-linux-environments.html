单元 04 · 3–4 小时

Linux、环境与故障定位

目标：把“玄学环境问题”变成可复现的证据链，知道如何观察文件、进程、资源、动态库和 GPU 软件栈。

过关标准

  • 能正确处理 shell 引号、变量、管道与退出码。
  • 能检查文件权限、进程、信号、CPU、内存、磁盘和端口。
  • 能解释环境变量从父进程继承给子进程。
  • 能区分驱动、CUDA Toolkit、CUDA Runtime 与框架自带组件。
  • 能用固定顺序定位“代码错、环境错还是性能差”。

1. Shell 是程序，不是魔法

pwd
ls -lah
rg "pattern" src/
command_a | command_b
echo "$?"
  • 单引号通常禁止变量展开；双引号允许变量展开但保留空格。
  • 管道连接前一个进程的 stdout 与后一个进程的 stdin。
  • 退出码 0 通常表示成功，非 0 表示失败；自动化脚本必须检查。
  • 路径和变量要加引号，避免空格与通配符造成意外拆分。

2. 权限、进程与信号

ls -l script.sh
id
chmod u+x script.sh
pgrep -af train.py
ps -ef
kill -TERM <pid>
kill -KILL <pid>   # 最后手段

对文件，r/w/x 表示读、写、执行；对目录，它们分别关系到列出名称、修改目录项和穿越目录。不要用 chmod 777 掩盖所有权或父目录问题。

SIGTERM 给进程保存 checkpoint、刷新日志和释放资源的机会；SIGKILL 无法被捕获或清理。

3. 资源观察矩阵

问题命令你在找什么
CPU/负载top, uptime, mpstat单核满、系统负载、上下文切换
主机内存free -h, vmstat可用内存、swap、页活动
进程内存pmap -x PIDRSS、映射、共享库
磁盘df -h, du -sh, iostat容量还是 I/O 吞吐
网络ss -lntp, curl -v, nc -vz监听、路由、握手、端口
GPUnvidia-smi驱动、设备、显存、进程

“内存不够”可能指主机 RAM、GPU 显存、/dev/shm、地址空间限制或磁盘。先确认资源种类。

4. 动态库与环境继承

which python
type -a python
python -c "import sys; print(sys.executable)"
ldd build/app
readelf -d build/app
env | sort

环境变量由父进程复制给子进程。修改 shell 配置不会改变已运行的终端、IDE、服务或 Jupyter kernel。动态库搜索还受到 RPATH/RUNPATH、系统缓存与默认目录影响。

5. 隔离工具解决不同层次

工具主要隔离不能保证
venvPython 包与解释器环境系统库、GPU 驱动
condaPython 与部分原生依赖宿主内核与驱动
容器用户态文件系统和依赖宿主 GPU 驱动与硬件

6. GPU 软件栈固定诊断顺序

  1. nvidia-smi：驱动能否看到设备？
  2. which nvcc 与 nvcc --version：Toolkit 来自哪里？
  3. which python 与 sys.executable：解释器来自哪里？
  4. torch.__version__ 与 torch.version.cuda：框架是什么构建？
  5. torch.cuda.is_available() 与设备数：框架实际看到什么？
  6. 自定义扩展再检查编译器、ABI、目标 GPU 架构和动态库。
nvidia-smi 成功但没有 nvcc不等于框架不能使用 GPU。运行预编译框架通常只需要兼容驱动；编译自定义 CUDA 代码才需要 Toolkit。

7. 可复现问题报告

最小报告必须包含：完整命令、完整错误、工作目录、输入规模、版本、硬件、环境来源、预期与实际结果、最小复现和最近一次变量变化。一次只改变一个变量。

git status --short
git diff --check
git diff

实验：环境审计

  1. 运行 environment_audit.py。
  2. 保存输出并标注解释器、包、GPU、编译器和动态库层。
  3. 人为切换一个 Python 环境，比较两次输出。
  4. 写出不使用“重装一切”的定位顺序。
