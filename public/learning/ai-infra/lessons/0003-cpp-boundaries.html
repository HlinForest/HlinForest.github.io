1. 内存模型：先问谁拥有

T* 是地址，不携带长度与所有权；T& 是已有对象的别名，通常不为空；std::span<T> 是“指针 + 长度”的非拥有视图。视图有效的前提是底层对象仍然存活。

void scale(std::span<float> values, float factor) {
    for (float& value : values) value *= factor;
}

二维行主序矩阵的线性偏移：offset = row * num_cols + col。这个公式同时决定 CPU cache locality 与 GPU 合并访存。

表达含义风险
T*可空地址长度、所有权、生命周期不明确
T&非空别名被引用对象可能先销毁
std::vector<T>拥有连续数据扩容使旧指针失效
std::span<T>非拥有连续视图底层存储必须仍有效

2. RAII：让作用域管理资源

RAII 把资源获取放进构造，把释放放进析构。无论正常返回还是异常展开，局部对象都会销毁，因此资源边界不依赖人工记忆。

class Buffer {
public:
    explicit Buffer(std::size_t n)
        : data_(std::make_unique<float[]>(n)), size_(n) {}
    std::span<float> view() { return {data_.get(), size_}; }
private:
    std::unique_ptr<float[]> data_;
    std::size_t size_;
};
  • unique_ptr：唯一所有权，可移动不可复制。
  • shared_ptr：共享所有权，有原子引用计数与环风险。
  • weak_ptr：观察共享对象但不延长生命周期。

默认优先值语义、容器和 unique_ptr。只有确实需要共同决定生命周期时才使用 shared_ptr。

3. 拷贝、移动与 const

拷贝产生独立状态；移动转移资源句柄，源对象仍有效但状态未指定。若成员都能正确管理自己，遵守 Rule of Zero：不手写析构、拷贝和移动特殊成员。

const 是接口契约：只读引用避免复制，也表达函数不会修改对象。性能接口最危险的是“看起来是视图，实际隐式复制”。

阶段典型报错优先检查
编译not declared / 类型不匹配声明、模板、头文件
链接undefined reference定义、链接库、符号签名
装载cannot open shared object搜索路径、架构、ABI

ABI 规定调用约定、名称修饰、对象布局和标准库二进制细节。编译器、标准库、编译选项或架构不同，都可能让“源码能编译”的组件无法一起运行。

5. CMake 与目标思维

cmake_minimum_required(VERSION 3.20)
project(buffer_lab LANGUAGES CXX)
add_executable(buffer_lab main.cpp)
target_compile_features(buffer_lab PRIVATE cxx_std_20)
target_compile_options(buffer_lab PRIVATE -Wall -Wextra -Wpedantic)

现代 CMake 围绕 target 管理编译选项、包含目录和链接依赖；不要把所有配置堆成全局变量。

6. Python/C++ 边界检查表

  1. dtype 是否完全一致？
  2. shape 与 stride 是否符合实现假设？
  3. 数据在 CPU 还是 GPU？
  4. 视图还是复制？谁保持底层存储存活？
  5. 异常如何翻译回 Python？
  6. 长计算是否释放 GIL？
  7. 调用粒度是否足够大，能摊薄边界开销？
“零拷贝”不是属性，而是一组条件。只要 dtype 转换、布局整理、设备搬运或生命周期不匹配，就可能发生复制。
